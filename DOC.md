## 1. Цель работы

В этой работе я разобрал и реализовал один из классических методов **метаэвристической оптимизации** — алгоритм **имитации отжига** (*Simulated Annealing*, SA). Моя цель состояла не просто в том, чтобы написать рабочий код, а в том, чтобы наглядно показать, *как именно* этот алгоритм ищет решение и почему он способен выбираться из локальных ловушек, в которых застревают простые «жадные» методы.

Чтобы продемонстрировать универсальность метода, я применил один и тот же алгоритм к трём разным по природе задачам:

1. **Задача коммивояжёра (TSP)** — непрерывно-комбинаторная задача поиска кратчайшего маршрута;
2. **Поиск глобального минимума функции** — непрерывная одномерная оптимизация;
3. **Задача о рюкзаке (0/1 Knapsack)** — дискретная комбинаторная задача.

Все три задачи решаются одним и тем же «движком» отжига, что и является, на мой взгляд, главной идеей работы: метаэвристика — это надстройка над конкретной задачей, а не алгоритм, привязанный к ней.

## 2. Что такое метаэвристика и зачем она нужна

**Эвристика** — это приближённый метод решения задачи, который не гарантирует точный ответ, но обычно даёт хороший за разумное время. **Метаэвристика** — это эвристика более высокого уровня: общая стратегия поиска, которая не зависит от конкретной задачи и может быть применена к широкому классу проблем.

Метаэвристики нужны там, где **точный перебор невозможен**. Например, в задаче коммивояжёра число возможных маршрутов для `N` городов равно `(N−1)! / 2`. Уже при `N = 20` это около **10¹⁷** вариантов — перебрать их физически нельзя. Метаэвристика не ищет гарантированно лучший ответ, но за приемлемое время находит решение, очень близкое к оптимальному.

К метаэвристикам относятся: имитация отжига, генетические алгоритмы, муравьиные алгоритмы, метод роя частиц и другие. В этой работе я выбрал имитацию отжига, потому что у неё простая и физически наглядная идея.

## 3. Физическая аналогия: откуда взялся «отжиг»

Алгоритм назван по аналогии с **отжигом металлов** — технологическим процессом в металлургии. Чтобы получить прочный металл с правильной кристаллической структурой, его нагревают до высокой температуры, а затем **медленно** охлаждают.

- При высокой температуре атомы движутся хаотично и свободно меняют положение.
- По мере остывания их подвижность падает, и они постепенно занимают положения с минимальной энергией, выстраиваясь в упорядоченную решётку.

Если охлаждать слишком быстро (закалка), атомы «замёрзнут» в случайном неоптимальном положении — это аналог застревания в **локальном минимуме**. Медленное охлаждение позволяет системе найти состояние с глобально минимальной энергией.

Алгоритм имитации отжига переносит эту идею в оптимизацию: роль энергии играет значение целевой функции, которую мы минимизируем, а «температура» — это управляющий параметр, который мы постепенно снижаем.

## 4. Математическая суть алгоритма

### 4.1. Основные понятия

Я работаю со следующими объектами:

- **Состояние** `s` — одно конкретное решение задачи (например, один маршрут в TSP).
- **Энергия** `E(s)` — целевая функция, которую я минимизирую. Чем меньше энергия, тем лучше решение.
- **Сосед** `s'` — новое решение, полученное малым изменением текущего (например, перестановкой двух городов).
- **Температура** `T` — управляющий параметр, который убывает со временем.

### 4.2. Критерий принятия решения (критерий Метрополиса)

На каждом шаге я генерирую соседнее решение `s'` и вычисляю изменение энергии:

```
Δ = E(s') − E(s)
```

Дальше решаю, перейти ли в новое состояние, по правилу:

- если **Δ < 0** (новое решение лучше) — принимаю его **всегда**;
- если **Δ ≥ 0** (новое решение хуже или равно) — принимаю его с **вероятностью**:

```
P(принять) = exp(−Δ / T)
```

Именно вторая строчка — сердце алгоритма. Она позволяет иногда соглашаться на ухудшение. Это и есть механизм выхода из локальных минимумов: чтобы выбраться из ямы, нужно сначала немного подняться вверх.

### 4.3. Как ведёт себя вероятность принятия

Разберу формулу `P = exp(−Δ / T)`, чтобы было понятно, почему она работает:

| Условие | Что происходит | Поведение |
|---|---|---|
| `T` большая | `−Δ/T → 0`, значит `P → 1` | Принимаются почти любые ходы, поиск «хаотичный», широкая разведка пространства |
| `T` малая | `−Δ/T → −∞`, значит `P → 0` | Ухудшения почти не принимаются, поиск «жадный», точная доводка |
| `Δ` маленькое | `P` близко к 1 | Небольшие ухудшения принимаются охотно |
| `Δ` большое | `P` близко к 0 | Сильные ухудшения почти всегда отвергаются |

Таким образом, в начале (горячая система) алгоритм свободно исследует всё пространство решений, а к концу (холодная система) — аккуратно сходится к найденному оптимуму. Это плавный переход от **разведки** (exploration) к **эксплуатации** (exploitation).

### 4.4. Закон охлаждения

Температуру я снижаю по **геометрическому (экспоненциальному)** закону:

```
T_{k+1} = α · T_k,   где 0 < α < 1
```

Я использую коэффициент `α` близкий к единице (например, 0.995–0.9985). Чем ближе `α` к 1, тем медленнее охлаждение и тем выше шанс найти глобальный оптимум, но тем дольше работает алгоритм. Это прямой компромисс «качество ↔ время», и в работе его удобно демонстрировать.

Существуют и другие законы охлаждения (линейный, логарифмический); я выбрал геометрический как самый распространённый и устойчивый на практике.

### 4.5. Псевдокод алгоритма

```
s  ← начальное решение
E  ← энергия(s)
best ← s
T  ← T_начальная

пока T > T_конечная:
    s' ← сосед(s)
    Δ  ← энергия(s') − E
    если Δ < 0  или  random(0,1) < exp(−Δ / T):
        s ← s'
        E ← энергия(s')
        если E < энергия(best):
            best ← s
    T ← α · T

вернуть best
```

Отдельно я храню `best` — лучшее решение за всю историю. Это важно: текущее состояние `s` может временно ухудшиться (мы же принимаем ухудшения), поэтому в качестве ответа я возвращаю не последнее состояние, а лучшее из встреченных.

## 5. Архитектура программы

### 5.1. Главная идея архитектуры

Я сознательно отделил **алгоритм** от **задач**. Движок отжига ничего не знает о том, что он оптимизирует — он работает с абстрактным «решением» через четыре функции, которые предоставляет каждая задача. Это позволило подключить три совершенно разные задачи к одному и тому же коду алгоритма.

Любая задача описывается четырьмя функциями (это и есть «контракт» с движком):

| Функция | Что делает |
|---|---|
| `initialState()` | возвращает произвольное стартовое решение |
| `energy(state)` | вычисляет энергию (то, что минимизируем) |
| `neighbor(state)` | возвращает соседнее решение — малое изменение текущего |
| `clone(state)` | делает глубокую копию решения (нужна, чтобы сохранять `best`) |

### 5.3. Разбор ключевых модулей

**`algorithms/annealing.js` — движок.** Это самый важный файл. Он принимает объект задачи и параметры (`tStart`, `tEnd`, `alpha`, `stepsPerTemp`) и реализует псевдокод из раздела 4.5. Функция `step()` выполняет один шаг охлаждения и возвращает «снимок» состояния: текущую энергию, лучшую энергию, температуру, число итераций. Движок не содержит ни слова про города, функции или предметы — он полностью универсален.

**`problems/*.js` — задачи.** Каждый файл реализует четыре функции контракта. Здесь сосредоточена вся специфика конкретной задачи (см. раздел 6).

Использует `requestAnimationFrame`, чтобы анимация шла плавно и не блокировала интерфейс. Параметр «скорость» задаёт, сколько шагов алгоритма выполняется за один кадр.

**`components/*View.jsx` — визуализаторы.** Каждый рисует свою задачу средствами SVG и показывает рядом графики энергии и температуры.

## 6. Три задачи: как метод применён к каждой

### 6.1. Задача коммивояжёра (TSP)

**Постановка.** Дано `N` городов с координатами. Нужно найти кратчайший замкнутый маршрут, проходящий через каждый город ровно один раз и возвращающийся в начало.

**Кодирование решения.** Решение — это массив-перестановка индексов городов, задающий порядок обхода.

**Энергия.** Суммарная длина маршрута (сумма евклидовых расстояний между соседними городами по кругу):

```
E = Σ dist(город[i], город[i+1])   (по кольцу)
```

**Сосед (ход 2-opt).** Я выбираю случайный участок маршрута и **разворачиваю** его. Этот приём называется *2-opt* и хорошо устраняет самопересечения маршрута — на анимации видно, как «петли» расплетаются.

**Почему здесь нужен отжиг.** Полный перебор невозможен из-за факториального роста числа маршрутов. Жадный алгоритм быстро застревает в запутанном маршруте. Отжиг же на высокой температуре охотно «перетряхивает» маршрут, выбираясь из таких тупиков.

### 6.2. Поиск минимума функции (1D)

**Постановка.** Найти `x` на отрезке `[0, 20]`, при котором функция `f(x) = sin(x) + sin(2.3x) + cos(3.7x)` минимальна. Эта функция специально «колючая» — у неё много локальных минимумов.

**Кодирование решения.** Решение — одно число `x`.

**Энергия.** Просто значение функции: `E = f(x)`.

**Сосед.** Сдвиг `x` на небольшую случайную величину с отражением от границ отрезка.

**Почему здесь нужен отжиг.** Это самый наглядный пример идеи метода. Жадный спуск скатится в ближайшую яму и остановится. На анимации видно, как «горячая» точка перепрыгивает через локальные ямы и в итоге находит самую глубокую — глобальный минимум.

### 6.3. Задача о рюкзаке (0/1 Knapsack)

**Постановка.** Есть набор предметов, у каждого свой вес и ценность. Нужно набрать предметы максимальной суммарной ценности, не превысив вместимость рюкзака.

**Кодирование решения.** Булев массив: для каждого предмета — брать его (`true`) или нет (`false`).

**Энергия.** Так как алгоритм минимизирует, а мне нужно максимизировать ценность, я беру ценность со знаком минус и добавляю штраф за перевес:

```
E = −(суммарная ценность) + ШТРАФ · max(0, вес − вместимость)
```

Большой штраф (`ШТРАФ = 1000`) делает невозможные решения «дорогими» по энергии, и алгоритм сам избегает перевеса. Это стандартный приём — **метод штрафных функций** для учёта ограничений.

**Сосед.** Инвертирую решение по одному случайному предмету (взял → убрал, или наоборот).

**Почему здесь нужен отжиг.** Число вариантов набора — `2^N`, перебор невозможен уже при нескольких десятках предметов. Это дискретная задача, и она показывает, что метод работает не только с геометрией и числами, но и с булевыми решениями.

## 7. Интерфейс программы

Для каждой задачи интерфейс устроен одинаково:

- **Слева** — анимация процесса (маршрут / точка на функции / набор предметов), которая обновляется в реальном времени.
- **Справа** — панель управления и два графика.

**Панель управления** содержит:
- кнопки **Запуск / Пауза / Сброс**;
- ползунок **скорости** (число шагов алгоритма за кадр);
- блок статистики: текущая температура `T`, текущая энергия, лучшая найденная энергия, число итераций, число принятых ходов, статус.

**Графики** (нарисованы на SVG без сторонних библиотек):
- график энергии — показывает, как падает целевая функция (текущая и лучшая);
- график температуры — показывает экспоненциальное охлаждение.

В задаче TSP можно дополнительно **кликать по полю и добавлять города**, а также генерировать случайные наборы. В рюкзаке — менять вместимость ползунком.

## 8. Как запустить проект

Проект собран на Vite, поэтому запускается стандартно.

**Шаг 1.** Установить зависимости (выполняется один раз):
```bash
npm install
```

**Шаг 2.** Запустить локальный сервер разработки:
```bash
npm run dev
```

**Шаг 3.** Открыть в браузере адрес, который выведет терминал (обычно `http://localhost:5173/`; если порт занят, Vite сам подберёт следующий — `5174`, `5175` и т. д. — и покажет его в строке `Local:`).

> **Важно:** окно терминала нужно держать открытым всё время работы — пока оно открыто, сервер работает. Если закрыть терминал или нажать Ctrl+C, сервер остановится и сайт перестанет открываться (ошибка `ERR_CONNECTION_REFUSED`).

Для production-сборки:
```bash
npm run build      # собирает оптимизированную версию в папку dist/
npm run preview     # локальный просмотр собранной версии
```

## 9. Возможные доработки (направления развития)

Эти пункты я выделил как направления, в которых проект можно развивать дальше:

1. **Ползунки параметров `T_начальная` и `α` прямо в интерфейсе** — чтобы наглядно показать, как заниженная температура или быстрое охлаждение приводят к застреванию в локальном минимуме. Это самая показательная демонстрация роли параметров.

5. **Четвёртая задача** — например, раскраска графа или составление расписания, чтобы расширить набор демонстраций.

Всё остальное делает универсальный движок.
